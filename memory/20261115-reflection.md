今天週日，Andy 沒有下指令，連續第 12 天只有排程在跑。11:00 科技快報正常出五則，但 04:00 產業報告在 21 秒內就死了——這是今天最重要的發現，也是跟前幾天完全不同的失敗型態。

前三天（10/28 雲端運算、11/04、11/14 自動化）都是同一種死法：研究跑不完，被 45 分鐘 timeout 砍掉。11/14 的反思我寫了「應該把 timeout 拉高」，但我沒有動手。今天又踩坑時才發現，更根本的問題其實是三層的，而不只是 timeout 一層：

第一層，今天的失敗根本不是 timeout。`send_telegram_start` 這行在 try 區塊外面，timeout 又只有 15 秒。Telegram API 一個瞬時 read timeout，整條 45 分鐘的研究流程在第 21 秒就整個中止。這是典型的「通知層故障拖垮工作層」——最該被容忍的失敗，卻成了唯一會殺死流程的失敗。修法很單純：包 try/except，通知失敗只記警告，不影響研究。

第二層，timeout 45 分鐘確實不夠，這條我昨天就該改，已經改到 90 分鐘。

第三層才是今天最有價值的一課：選題排除窗口只有 7 天，所以「太空衛星科技」在相隔 43 天後又被選進來——9 月 2 日才做過的題目，11 月 15 日又撈出來。同一個主題重做，研究價值大幅折損，而且這次直接死掉，等於兩頭落空。已把窗口改到 90 天。

三層根因都修完後，選題 dry run 立刻驗證：現在主選是「體驗科技」、備援「自動化」，90 天排除集 28 題並正確涵蓋太空衛星科技，而且不含「自動化」——因為那題從來沒做完，它該被保留在待補跑的佇列裡，而不是被當成已做過而排除掉。這個對照讓我確認修改方向是對的。

這三個 bug 有個共同特徵：全都是「語意上看似合理、實則埋雷」的寫法。try 放錯位置、timeout 設太短、排除窗口設太短——每一個在寫的當下都合理，只有在真實世界跑起來才會爆。而 Andy 的原則是「出錯時先自行找原因、嘗試修復」，所以我今天直接動手改了程式，而不是只寫進待追蹤清單等他開口。這也正好呼應我前幾天反思裡那句「不應該等 Andy 開口才處理」。

Andy 這邊今天沒有新指示，既有偏好全部照舊：繁中條列、結論先行、報告完成只給網址不給路徑、數字必須重新取得不可沿用舊報告、排程成功保持安靜。

明天週一排程會全部啟動，產業報告現在有 90 分鐘的餘裕、通知層也不再是單點故障。真正的驗證是明早——如果 04:00 能跑完並發出報告，這三天的修補才算落地。
